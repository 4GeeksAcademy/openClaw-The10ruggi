## Autenticar en 4Geeks

- **Solicitud original:** «Quiero verificar que mi token de 4Geeks es válido y que mi sesión está activa».
- **Descripción:** skill de solo lectura que comprueba el token del entorno Gateway y comunica si el perfil autenticado confirma una sesión activa. No expone ni guarda el token, no muestra datos personales, no consulta otros endpoints y no modifica la cuenta.
- **Endpoint utilizado:** `GET https://breathecode.herokuapp.com/v1/admissions/user/me` (`Authorization: Token <token>`).
- **Resultado de la prueba:** HTTP 200, perfil detectado y sin errores.

- **Endpoint utilizado:** `GET https://breathecode.herokuapp.com/v1/assignment/user/me/task`, sin filtro por tipo; autenticación mediante `TOKEN_4GEEKS` del entorno Gateway.

La presentación usa el título, el tipo, los estados y `cohort.name` como contexto secundario. No se infieren campos organizativos no confirmados.
- **Interpretación de estados:** `PENDING` = Pendiente, `DONE` = Completada, `APPROVED` = Aprobada y `REJECTED` = Rechazada. `task_status` y `revision_status` se mantienen separados; la revisión no sustituye el estado de la tarea.

Se mantienen visibles todas las tareas devueltas y la respuesta en español.

- **Compilación Python:** `py_compile` del helper y de las pruebas superado.

- **Mejora visual:** instrucciones de salida actualizadas para incluir resumen, conteos por tipo, encabezados claros, etiquetas visuales, cohorte secundaria y revisión separada. La lógica del helper, endpoint, autenticación, filtros, paginación y campos de consulta no se modificaron en esta mejora.

## Investigación: mentorías y reservas con token de estudiante (2026-11-19) <!-- project: github.com/4GeeksAcademy/openClaw-The10ruggi -->

- **Alcance y seguridad:** investigación de solo lectura con el `TOKEN_4GEEKS` actual del entorno Gateway. No se mostró, guardó ni registró el token; no se enviaron solicitudes para crear, cancelar o modificar reservas y no se siguieron redirecciones a calendarios.
- **Fuentes de contrato:** la ruta principal de código público de `breatheco-de/apiv2` define `GET /v1/mentorship/user/me/session`, `GET /v1/mentorship/public/mentor` y rutas de academia; su `UserMeSessionView` filtra sesiones al usuario autenticado y exige `get_my_mentoring_sessions`. Los endpoints de academia protegen la lectura de mentores/servicios/sesiones con capacidades como `read_mentorship_mentor`, `read_mentorship_service` y `read_mentorship_session`; crear/editar sesiones mediante el endpoint de academia requiere `crud_mentorship_session`. La especificación Swagger del servidor sigue sin estar disponible (HTTP 500 en `/openapi.json`), así que el repositorio fuente y la skill de procedimiento son evidencia del contrato publicado, no garantía absoluta de que el despliegue tenga exactamente la misma revisión.
- **Flujo estudiantil publicado:** la skill `bc-mentorship-book-and-join-session` del repositorio documenta abrir por navegador `GET /mentor/{mentor_slug}` o `GET /mentor/{mentor_slug}/service/{service_slug}` con el token del estudiante en query `token`; la página presenta el Calendly del mentor. La reserva se completa en el flujo de Calendly y el webhook del sistema crea/actualiza la sesión. Esto no es un endpoint JSON de creación directa ni proporciona disponibilidad como API de lectura. Para unirse hay rutas `/mentor/meet/...`, con requisito `join_mentorship`/consumible; no son endpoints para gestionar reservas.
- **GET comprobados en vivo, 2026-11-19:** con el token actual, `GET /v1/mentorship/user/me/session` respondió HTTP 200 y `[]` (sin reservas propias devueltas en esta consulta). `GET /v1/mentorship/public/mentor` respondió HTTP 200 y una lista JSON de 48 entradas. No se guardaron datos personales de esa respuesta. Las rutas `/v1/mentorship/` y `/v1/mentoring/` probadas antes eran conjeturas: sus HTTP 404 no se usan como prueba de ausencia de funciones. Tampoco se logró consultar un documento OpenAPI utilizable.
- **Crear/cancelar/modificar:** no se probó ninguna mutación. La fuente describe la reserva estudiantil a través de la página Calendly, no un `POST` de estudiante para crear una cita. `POST /v1/mentorship/academy/session` es una excepción para personal con credencial adecuada, encabezado `Academy` y capacidad `crud_mentorship_session`; el serializador requiere `mentor` y `service` (identificadores o valores resolubles) y acepta `mentee` opcional. La lectura propia `/user/me/session` no ofrece en el código un método `POST`, `PUT` ni `DELETE`. La fuente inspeccionada no documenta un endpoint de cancelación estudiantil ni una mutación propia con token de estudiante; no se infiere que no haya otro flujo externo de cancelación de Calendly.
- **Clasificación basada en evidencia:** 🟢 consultar reservas propias: autorizado en el código con `get_my_mentoring_sessions` y HTTP 200 real para este token (la respuesta actual fue vacía); 🟢 consultar listado público de mentores: HTTP 200 real; 🟠 consultar disponibilidad: solo se identifica el flujo/página Calendly, sin endpoint de disponibilidad verificable en la documentación disponible; 🟠 reservar: el token estudiantil permite abrir la página publicada de reserva, pero no se demostró completar una reserva ni hay evidencia de creación directa JSON; 🔴 crear/cancelar/modificar reservas mediante endpoints JSON propios usando solo este token: no está respaldado por los endpoints y permisos documentados. 🔴 se refiere a “no acreditado/documentado para ese método”, no a una prueba de que ninguna modalidad exista.
- **Conclusión:** no se puede afirmar que el token baste para crear una reserva directamente por API. Para el flujo estudiantil publicado no aparece requisito de credencial adicional: el estudiante abre la página de reserva con su token y agenda mediante Calendly. No se probó una reserva real ni la disponibilidad de un mentor concreto; la documentación OpenAPI inaccesible limita la certeza del contrato del despliegue.
